# GEP-0000: the proposal process & the gap register

Two things in one founding document: the **GEP process** (gnx enhancement proposals, in the style of Rust RFCs), and the **gap register** — the output of a full reasoning pass over the composition grammar, the manifest format, and the components actually in the catalog. The register is the GEP queue: each gap that needs a decision becomes a proposal.

---

## The process

A GEP is the unit of design decision. Discussion happens in the open; a decision that survives becomes doctrine, then specification. The format, adapted from Rust RFCs:

| Section | Carries |
|---------|---------|
| Summary | one paragraph |
| Motivation | the gap or force; what breaks if it stays undecided |
| Guide-level explanation | the change as a user or author would meet it |
| Reference-level explanation | the precise semantics — the part a spec can cite |
| Drawbacks | why not to do this |
| Rationale and alternatives | what else was considered, and why this |
| Prior art | what other ecosystems did (Cargo, Kubernetes, protobuf, npm) |
| Unresolved questions | what stays open past acceptance |

Statuses: `draft → proposed → accepted | rejected | superseded-by:<n>`. The **document status line** (the bold line under each GEP title) carries the lifecycle; the frontmatter `status:` stays within the site-wide maturity enum (`proposed` while a GEP is a proposal, `mixed` once accepted but not yet tool-enforced) so the machine-readable honesty layer keeps one vocabulary. An accepted GEP amends doctrine and unblocks the specifications that cite it. Numbering is append-only; a dead GEP keeps its number — the same alias-and-lineage discipline the identity grammar applies to components, applied to our own process.

This gives grammar and catalog design decisions a chartered home: **the GEP register is where they get made.**

## The gap register

Method: the shipped grammar (slick's five-field Manifest), the designed model, the public docs, the CLI surface, and the real components in the catalog were held against each other. A gap is registered when the artifacts disagree, or when a semantics the build path needs does not exist anywhere.

**Most of these gaps are scoped, not un-researched.** The direction is usually settled; what is open is the exact format or the precise semantics. A GEP's job is to *close and cite*, not to re-derive from scratch. Where prior work already owns a decision, the GEP inherits it rather than re-opening it.

**The headline pattern:** the doctrine layer — why a catalog, why governed composition, why vendor-neutrality — is complete and coherent. The gaps concentrate in the **normative layer of the grammar** — the exact formats and semantics — and every load-bearing gap sits precisely on the build path: each one is hit the moment another component registers or the first components are wired together. The real components already stress several of them.

### Tier 1 — load-bearing logic gaps

**G1 — Component identity has no normative spec, and the catalog already breaks its own convention.**
`type_url` is the single join key of the whole system — and it was documented by example only, with the examples in open disagreement (the reference once showed PascalCase resource names; every real component on disk is kebab-case, `gnx.dev.v1.intent-hardening`). The envelope uses slash-form (`slick.dev/v1`) while `type_url` uses dots, and the derivation rule between them was left open. Portability computation needs a rule for extracting the namespace from an identity. This decides the most load-bearing string in the system — now ruled kebab-case. → **GEP-0001** *(accepted)*

**G2 — The `provides` value-space is double-typed.**
One page of the docs treats `provides` entries as typed ports; an adjacent section treats them as free discovery tags. The real components use dotted-phrase tags (`intent.hardening`) with no schemas behind them. If tags are free strings, tag drift becomes search-side pollution (`session-memory` vs `memory`). If they are typed ports, every semantic tag would need a schema, which is absurd. This decides whether the catalog needs a controlled discovery vocabulary. → **GEP-0002** *(accepted)*

**G3 — The composition kind has no documented shape.**
The composition artifact (a Flow) has no manifest format anywhere: how members are declared, how ports bind, where a cycle's declared bound attaches, whether Flows nest, what a Flow's own ports are derived from. This is the largest completeness hole in the grammar. → **GEP-0003** *(proposed)*

**G4 — Three dependency notions are squeezed into two fields.**
(a) *dataflow input* — what a node consumes at runtime; (b) *install dependency* — what must be present for a component to install; (c) *soft dependency* — the `relations.uses` edge (intent-hardening uses rational-inquiry). These have different satisfaction times, different failure modes, and different transitive behavior — yet the only real dependency in today's catalog lives in `relations`, which has no defined semantics. Does installing intent-hardening pull rational-inquiry? Currently unanswerable. → **GEP-0004**

**G5 — `relations` is the most overloaded field with no vocabulary.**
Keys observed across the corpus: `skills`, `uses`, `tested_with`, `replaces` — plus the candidates the open questions imply: an accreditation edge, a supersession edge. It is a `map[string][]string` with no key registry, no transitivity rules, no install behavior — simultaneously where skills travel, where lineage would live, and where accreditation might attach. The highest-consequence field with the least definition. → **GEP-0004**

### Tier 2 — kind-completeness gaps

**G6 — The Agent kind is underspecified to near-vapor.**
Capability and Skill have real definitions; Agent has one sentence — "a named reasoning role with a distinct method" — and no declared surface: no ports, unspecified protocol, unspecified configuration. The live examples cut against the kind, invoking an agent registry-style like a Capability. When a Flow needs an agent node, what surface wires it? → **GEP-0005**

**G7 — Frontend / surface components have no worked semantics — by design, but unnamed.**
The core kinds cover runnable, reasoner, knowledge, and composition. A UI panel or legibility view is none of them — and that is exactly what the vendor-namespace extension mechanism is *for*: a surface component would be a vendor-runtime kind, or a Capability whose protocol is a serving transport. The core stays small; nobody has yet worked out what a surface component *declares* — what it consumes, what it provides, how portability computes for it. Not needed yet; needed the moment a runtime's view layer wants catalog components. → **GEP-0006** (stub now, worked when a runtime needs it)

### Tier 3 — evolution & selection gaps

**G8 — Versioning and evolution semantics are almost entirely absent.**
What change forces `v1 → v2`? No compatibility rules exist. Three version notions circulate — the `type_url` version segment, the plugin version (the install cache key), and the install pin — with unspecified relations. The rule "a new version is a new `type_url`" was stated in passing; it deserves proposal treatment plus the supersession machinery it implies (deprecation, a yank equivalent). → **GEP-0007**

**G9 — Selection and fan-in semantics are unscoped.**
A composer rejects two components producing the same type — but the catalog's entire point is N components providing the same interface. So single-producer must be scoped **per composition**, not per catalog. And when several installed components provide X and one is required: who selects, on what signal? → folds into **GEP-0003** (composition semantics) plus a selection note in the registry spec

**G10 — The accreditation record has no schema.**
Two-axis verdicts (grounding and warrant) — over what value-space? A content hash plus authority plus detached signature — of what content, normalized how? Whether accreditation is a relation, a kind, or a side-table is unpicked. Ready to draft; final acceptance blocked on the signing-authority decision. → **GEP-0008**

**G11 — The projection loses component identity; round-trip unspecified.**
Claude Code knows plugins; accreditation, portability, and maturity are per-component. Whether the projected plugin tracks its installed components individually — whether it emits a component lockfile — is unspecified. An agent standing inside a projected plugin cannot currently enumerate which catalog components it is running. → folds into the projection spec + **GEP-0004**

**G12 — The on-disk overlay contract has no normative home.**
The on-disk format's extra fields (`kind`, `maturity`, and a missing `version`) exist today only as YAML comments in the real manifests. `version` has no home anywhere in the chain, while Claude Code uses the plugin version as its silent install cache key — and the projector hardcodes a fixed version, which means an installed user can never receive a content update: broken by construction. → **GEP-0009** *(proposed)*

### The completeness verdict

- **Docs vs doctrine:** consistent — the craft passes hold.
- **Doctrine vs normative grammar:** incomplete in twelve places, five of them load-bearing (G1–G5).
- **Grammar vs the actual catalog:** the real components surfaced G1 (casing — now ruled kebab-case), G2 (tag typing — now ratified), and G4/G5 (`uses` semantics — still open). The dogfood found the gaps; the register named them; G1 and G2 are closed.
- **Sequencing:** G1 and G2 gate the next component's registration; G3–G5 gate the first real composition; G8–G10 gate the registry build. None gate the docs or the projection of standalone plugins. Mass registration of adopted tooling sits behind G1/G2 — both now accepted, both hour-scale convention rulings.

## Unresolved questions

- Whether the GEP register stays public permanently. It is published openly now — open design in the open — and retreats to the internal wing only if it confuses more than it invites.
- Which GEPs slick co-owns at ratification (G1 and G3 at minimum — the proposals are gnx's, the ratification is shared).
- Whether GEP acceptance eventually requires a formal review gate, or whether open-margin consensus suffices at the current fidelity. Lean: margins now, a gate once the registry is live.
