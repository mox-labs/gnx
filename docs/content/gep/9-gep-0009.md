# GEP-0009: the on-disk overlay contract

**Proposed — ratification pending; the maturity value-space names are still owed a mint. Addresses G12 (the on-disk overlay contract). Numbering note: 0004–0008 are reserved by GEP-0000's gap mapping, so this takes the next free number, append-only.**

## Summary

gnx's on-disk manifest is **slick's five fields plus exactly three overlay fields common to every kind**: `kind` (a provisional literal), `maturity` (with a projection gate), and `version` (the single source of truth for content revision). The overlay is a gnx-side contract **by construction, not preference** — slick's own MSG header routes governance-adjacent metadata off the Manifest — and because the crate cannot see the overlay, the **gnx linter carries its entire validation burden**. Intake conventions bind to this contract: metadata is re-stamped, never copied; one `produces` per component; self-description travels with the artifact. (Kind-specific fields — like the Flow `members` list GEP-0003 proposes — are separate proposals layered on this contract, not part of the common overlay.)

## Motivation

The overlay exists today only as YAML comments in the real manifests — `kind` and `maturity` are parsed by no code and defined in no doc. `version` has **no home anywhere in the chain**, while Claude Code uses the plugin version as its silent install cache key — and the projector hardcodes a fixed version, which means an installed user can never receive a content update. Broken by construction, today, without a registry in sight.

The evidence that this needs a *single* source of truth is in the lineage: an adopted tooling family's frozen state carries live three-way version drift — the same components showing one version in their registry and another in their plugin files, all committed in a deliberate wind-down. **Dual-source versioning failed under attentive curation.** The intake rule follows: re-stamp, never copy.

And `maturity` is the honesty discipline's load-bearing field — radix's manifest defends `design` over `shipped` in a thirty-line comment — yet the projector would project a design-stage component as an installable plugin today. The gate is missing, not the value.

## Guide-level explanation

An author writes slick's five fields and three more lines:

```yaml
type_url: gnx.dev.v1.recon       # minted per GEP-0001
kind: Capability                 # provisional literal — see Reference §1
maturity: shipped                # gates projection — see Reference §2
version: 0.8.0                   # THE content revision — flows to plugin.json
source: ./                        # the adopted tree
provides: [gnx.dev.v1.recon-report, recon.search]
requires: [gnx.dev.v1.target]
relations:
  skills: [./skills/recon/SKILL.md]
```

The linter enforces what the crate cannot. The projector reads `version` and `maturity`; the catalog reads all three.

## Reference-level explanation

1. **`kind`** — an open literal: `Capability | Agent | Skill | Flow` today, **explicitly provisional** pending the kind-count adjudication (4 vs 8 vs none vs a longer list). Two guards make provisionality safe: `kind` never enters `type_url` segments (GEP-0001 §3), and the linter enforces directory↔manifest agreement under the layout (`components/<kind-plural>/…`), so a reclassification is a `git mv` plus one field — a two-way door by construction.
2. **`maturity`** — observed values on disk: `shipped`, `design`. The value-space finalization is owed (the mint-once naming discipline applies to enum values too); the **gate is the normative part**: only `maturity: shipped` projects to an installable plugin by default; anything lower projects only under an explicit flag. This kills the live bug where a design-stage component (radix) would ship as an empty-but-installable plugin.
3. **`version` — the SSOT, and the version split.** Two versions exist and must never impersonate each other (the xDS lesson: the proto package version vs `version_info`):
   - the **`type_url` `<ver>` segment** — grammar-major, near-frozen, changes only on breaking identity-grammar revisions;
   - the **overlay `version`** — content revision, flows verbatim to `plugin.json`, and *is* the install cache key (the `version_info` analog).
   Intake re-stamps from the overlay; tool versions are sourced from their own manifests of record (`pyproject.toml`, `Cargo.toml`) at intake time; marketplace-file versions are dead text and are never read.
4. **Field names stay slick's five — today.** `provides` carries ports and tags under GEP-0002's shape rule. Explicit `consumes`/`produces` topology fields on the overlay are **deferred** until a real component needs a distinction the shape rule cannot carry (the first two-output component). Composers map catalog fields to runtime names — a runtime speaks `consumes`/`produces`; the mapping is the composer's, not the manifest's.
5. **Mechanical safety, both edges of it.** The slick crate has no `deny_unknown_fields`: the overlay round-trips through the crate untouched — which is what makes it a safe two-way door — and the same fact means **the crate can never validate overlay fields**. A typo'd `maturty:` vanishes silently everywhere except the gnx linter. The linter is not a nicety; it is the only validator this contract has.
6. **The MSG discipline — why an overlay and not slick fields.** The shipped header, verbatim: *"A Manifest is pure Mechanics in the MSG framework: **M (Manifest)**: identity, source, ports, relations — structure · **S (Skills)**: referenced via `relations["skills"]` — natural language · **G (Governance)**: external — not on the Manifest."* Every pressure to grow the slick core is answered on its own plane: governance metadata → the overlay (G), meaning → the payload (S), execution → the runtime (M). This GEP is the G-plane contract; it never touches the core.
7. **Intake conventions bound to this contract:** single-`produces` per component (a runtime's compile rule makes it free today); component-owned manifests — self-description travels with the artifact (the `--skill` doctrine), with the catalog recording the edge in `relations["skills"]`; metadata re-stamped at intake; per-component review at registration (nothing grandfathered — adopted tooling is input, not constraint).

**What this GEP does not decide:** the kind count; the projector contract and the lockfile-grade identity file (projection-spec territory); accreditation records (GEP-0008, blocked on the signing-authority ruling); Flow members (GEP-0003).

## Drawbacks

Overlay fields are invisible to ecosystem tooling written against the slick crate alone — accepted: the readers are the gnx linter, catalog, and projector, and the crate's blindness is the price of the two-way door. A third version notion (the install pin) arrives with the lockfile and must slot under the same split — flagged for the projection spec so it lands as a `version_info`-of-record, not a fourth truth.

## Rationale and alternatives

- **Grow slick core fields** — rejected: violates the shipped MSG boundary and the standing rulings ("slick never executes"; "stores, never interprets"); and an earlier deliberation's own re-add proposals (kind, description) never landed — the overlay route *is* the answer to them.
- **marketplace.json as version SSOT** — rejected: Claude Code ignores marketplace versions (verified mechanics), and the adopted family's drift is the empirical obituary.
- **No version until the registry exists** — rejected: the cache key breaks updates *now*, with real components and installed plugins.

## Prior art

xDS (`version_info` vs proto package version — the split, verbatim); Cargo (`Cargo.toml` as SSOT flowing to `Cargo.lock` — our lockfile story will rhyme); TypeScript over JavaScript (a gradual overlay the substrate never has to see — validate where the checker runs, which for us is the linter).

## Unresolved questions

- The `maturity` value-space's final names (owed — the mint-once discipline applies to enum values too).
- `kind` literals pending the kind-count adjudication — this contract survives any answer, including "none," by the two guards in §1.
- The lockfile-grade identity file's exact shape (projection spec; prefer a separate `gnx-lock` file over `x-gnx` keys in `plugin.json` — Claude Code's tolerance of unknown keys is unverified).
- Ratification owed: the three-field list itself, and the projection gate's default.
