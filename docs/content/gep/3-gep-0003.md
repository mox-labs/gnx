# GEP-0003: Flow is the composition root

**Proposed — ratification pending. This GEP closes the *shape* half of G3 and folds in G9's selection scoping; the cycle/leash half stays explicitly open (its primary source is currently unlocatable — see Unresolved).**

## Summary

A Flow manifest is its own five-field identity plus `kind: Flow` plus a **members list of TypedStructs** — `(type_url, optional config)` pairs. **Edges are never declared; topology is derived** from the members' port declarations at compile time. The same artifact serves two consumers: a runtime compiles and executes it; the projector resolves members against the catalog and emits **one plugin** — the N:1 project-plugin is a Flow projected. The shape is not invented here: it is the third independent derivation of the same design — empirically in a validated multi-agent ancestor, in a shipped composition runtime's code, and in xDS as the industrial precedent slick's registry layer was already modeled on.

## Motivation

The composition kind has no manifest form anywhere — GEP-0000 calls G3 "the largest completeness hole in the grammar": how members are declared, whether Flows nest, what a Flow's own ports derive from, where a cycle's bound attaches. Meanwhile the population task needs N:1 bundles *now* (a project-plugin assembling components into one installable unit), and the first-composition milestone needs a form a composer can read. The shape half is over-determined by the lineage; withholding it blocks real work to wait on the parts that genuinely are open (cycles, nesting).

## Guide-level explanation

```yaml
# components/flows/review-bench/manifest.yaml
type_url: gnx.dev.v1.review-bench
kind: Flow
source: ./manifest.yaml
provides:
  - review.bench                     # a tag (GEP-0002) — findability
requires: []
members:                             # the composition root — TypedStructs
  - type_url: gnx.dev.v1.rational-inquiry
  - type_url: gnx.dev.v1.intent-hardening
    config: { gradient: strict }
```

A runtime compiles it: resolves each member through the `type_url` registry, derives the DAG from the members' ports, validates (missing producer, duplicate output kind, cycles), schedules, executes. The projector packages it: resolves the same member `type_url`s against the catalog, pulls payloads, emits one self-contained plugin. **One artifact, two consumers** — and for projection, none of the unresolved runtime semantics matter, because the projector reads only `members`.

A Flow whose members share no port edges is **first-class, not degenerate**: it compiles to one parallel batch over the shared substrate. That is precisely how the validated multi-agent ancestor ran — several specialists, zero inter-agent dataflow, composition through the shared substrate.

## Reference-level explanation

1. **`members`** — an ordered list of TypedStructs: `type_url` (resolved per GEP-0001) plus optional opaque `config`. It is an overlay field: `relations` cannot carry it (a `map[string][]string` has no config payload). Order is informational only — execution order is computed.
2. **Topology is derived, never declared.** The reference runtime's shipped semantics: missing producer, duplicate output kind, duplicate name, and any cycle raise a compilation error before any work runs. Declared membership, computed wiring.
3. **Single-producer is scoped per composition** (the G9 fold-in). The compile-time one-producer-per-kind rule binds *inside a Flow*; the catalog's entire point is N providers of one interface. Selection among N installed providers at composition time is the composer's concern — a registry-spec note, not a manifest field.
4. **Config is defined-or-opaque, xDS-style.** A member's `config` validates against its `api/` schema when one exists, and rides as opaque TypedStruct until then, with the upgrade path when the schema lands. Opaque is the onboarding ramp; defined is the destination; neither blocks the other.
5. **N:1 projection.** A `gnx build` on a Flow resolves member `type_url`s, vendors payloads, and emits one plugin (projector-contract territory for mechanics: a lockfile-grade identity file, license passthrough). Composition stays the runtime's job; packaging stays the projector's; the two never blur.
6. **A Flow's own identity** is a catalog citizen like any component — accreditable, versionable (GEP-0009), supersedable. Promoted compositions get their provenance in `relations` (provenance discipline, deferred detail).

## Drawbacks

The ordered list implies an order that mostly doesn't matter — cosmetic confusion, accepted. Opaque configs cross unvalidated until `api/` schemas exist — accepted per the xDS ramp. And `members` is invisible to the slick crate (no `deny_unknown_fields` — it round-trips silently), so the gnx linter carries all validation, same as the whole overlay (GEP-0009).

## Rationale and alternatives

**The triple derivation** — why this shape is as settled as an unratified shape gets:

- **Empirically, in a validated multi-agent ancestor:** components declare needs and products; the orchestrator compiles topology and schedules batches; no inter-component messaging; and the engine-reuse finding — a grader is just another component — the evaluation harness was the same engine with different members loaded. Composition-as-configuration is the measured design, not an aesthetic.
- **In shipped runtime code:** a module names itself the composition root; its orchestrator builder takes a sequence of `(type_url, config)` pairs — that *is* the members list, running today.
- **xDS, as precedent:** `TypedExtensionConfig{name, typed_config: Any}`; filter chains are lists of them; the factory registry instantiates by `type_url`; invalid configs are NACKed at load. slick's TypedStruct/TypedRegistry are xDS-isomorphic by design — the members list is the same atom in a manifest.

One deliberate divergence from the precedent: xDS filter chains are **positional** — ordering is implicit semantics operators must simply know, a classic footgun. The Flow **derives** order. Keep the divergence; it is the better half of the design.

Alternatives rejected: **`relations.contains`** (no config payload; demote to an optional derived view for graph tooling if wanted). **Declared edges/bindings** (the lineage's whole lesson is that three systems *derive*; hand-wiring reintroduces the drift class the compiler exists to catch). **Flow as runtime-config only, no manifest** (the catalog must hold compositions as citizens — promoted, accredited, superseded).

**Cross-check against the design lineage (resolved).** GEP-0000 seeded this GEP with a note to excavate the most design-complete historical Flow sketch in the design lineage. That excavation has now run, and the sketch **disagrees** with this shape on three points: it carries no members list, it composes through `relations` (the alternative rejected above), and it uses a Kubernetes-style envelope dialect. The members-list shape stands regardless — it rests on the triple derivation, not on any single sketch — and the disagreement is recorded as *signal*, not overridden silently. The one point worth carrying forward: the sketch modeled its human-facing surface as **ports** (`requires: canvas-renderer`, `provides: showcase`). Whether a view/surface component is modeled as ports or as a relation is a live question — explicitly deferred to **GEP-0006**, which must rebut or adopt it.

## Prior art

Envoy xDS/ECDS (ECDS is the later story for dynamic member delivery — catalog-as-control-plane already accommodates it); dependency-injection composition roots (the runtime's own docstring names the pattern); the engine-reuse finding (evaluation Flows fall out free: an accreditation run is a Flow whose members include graders).

## Unresolved questions

- **Cycles and leashes.** The doctrine that would permit bounded cycles — condensing strongly-connected components behind an explicit leash — has no locatable primary source; the vocabulary survives only in derivative notes. Until it is recovered or re-derived, **reject-all-cycles is the validated baseline** (both the runtime and the multi-agent ancestor enforce it), and first Flows are acyclic by choice.
- **Nesting** — whether a Flow may be a member of a Flow. Deferred until one Flow has run.
- **A Flow's own `provides` derivation** — union of members (flat benches) vs terminal artifacts (pipelines). Deferred; observe the first real Flows.
- **Closed-world inputs** — every consumed kind needs an in-DAG producer today; external input enters via constructor config (the seed-input convention). A future steering mechanism that treats steering as consumed enrichment would break the closed world — runtime-milestone material.
