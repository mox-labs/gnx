# aboot — the continuity capability

## Continuity, not genesis

aboot manages session lifecycle events and continuity artifacts. It is not
init/genesis — that is `gnx init`'s job (the Claude Agent SDK interview that scaffolds
`claude + dao + .gnx/`). The distinction is the timing: init fires once at project
birth; aboot fires every session, for the life of the project.

Source: §6, corrected definition, 2026-06-12.

## The raw material already exists as personal tooling

Nothing here needs to be designed from scratch. The raw material exists as personal
tooling across three locations:

| Artifact | Location | Function |
|---|---|---|
| `write-resume.sh` | SessionStart hook | Generates `.claude/resume.sh` per repo |
| ratchet loader | guild-arch | Loads ratchet state across sessions |
| continuity discipline | research repo | `next-session-brief.md`, handoff-on-a-branch, continuity dumps |
| session-context pattern | scratch | Per-session context file read at start |

Componentization lifts this from personal scripts into a registered Capability
component with a declared surface, embedded skill, and `bin/aboot --skill`. None of
the underlying logic is new.

## The namespace split is the sharpest first test of the universal/vendor architecture

**Universal core** (`slick.dev/v1`): the continuity artifacts themselves — briefs,
handoffs, resume state, context dumps — and the protocol for when they are written and
read. This layer is runtime-agnostic. Any system with sessions and an agent needs this.

**Vendor binding** (`hooks.claude.anthropic.com/v1`): SessionStart, SessionEnd,
PreCompact, Stop. These are Claude Code's event vocabulary. The binding wires the
universal protocol to CC's hook system. A future harness (geist.sh, a different IDE
plugin, a CI runner) binds the same universal core to its own event names without
touching the core manifest.

The split is structural: `gnx validate` enforces that a `slick.dev/v1` component
cannot carry `hooks.claude.anthropic.com/v1` semantics in its `provides` tags. The namespace IS the enforcement boundary. If
SessionStart leaks into the core manifest's `provides`, it enters Dagstra's search
index. The catalog's composition graph becomes CC-shaped even for non-CC consumers. That is degeneration watch #1, and it is irreversible once the catalog
grows on a polluted index.

The practical question the split forces: what does the universal core actually
`provide`? Not "SessionStart handling" — that is CC vocabulary. Something like
`session-resume`, `continuity-brief`, `handoff-artifact`. The right tag vocabulary
for the universal provides surface is [open] and is itself a concrete exercise in
namespace discipline.

## The CC projection is the first concrete vendor binding

Projected onto Claude Code, the binding lands as:

```
.gnx/
└── aboot/
    ├── hooks/
    │   └── hooks.json         # CC hook registrations: SessionStart → bin/aboot resume
    ├── bin/
    │   └── aboot              # ships --skill; emits SKILL.md on request
    └── plugin.json            # generated by gnx build from component source
```

`hooks/hooks.json` is static — committed output of `gnx build`, not generated at
install time. §8 is explicit: no install-time build hook exists; plugins must be
self-contained. `gnx build --check` keeps CI honest if the source drifts from the
committed projection.

The embedded skill (`bin/aboot --skill`) is aboot's front door to Claude Code. Per
the hard catalog rule (§3): a Capability without an embedded skill is not
agent-operable and does not clear the curation bar. The skill declares what aboot
provides to agents — how to invoke resume, how to write a handoff brief, what to
expect in `.claude/resume.sh`.

## aboot directly exercises degeneration-watch #1

The watch (§8): "Manifest core accreting vendor semantics."

The risk is specific to aboot because it sits at the boundary where vendor event
names are most visible. Every other capability in the core set (ci-scaffolds,
guild-arch, antifragile) is invoked by the agent explicitly; aboot is invoked by CC's
hook system, which means the hook event names appear in the wiring. The temptation
to reference those names in the core manifest — for legibility, for convenience — is
real.

The defense is the two-manifest structure: universal core manifest never names hook
events; vendor binding manifest names them explicitly and points back at the core
through a relations entry ([open] — no settled doctrine names the exact field; ground
truth establishes the split, not the pointer). Degeneration-watch #1 has teeth only if
this structural separation is enforced at `gnx validate`, not left to authoring
discipline.

Degeneration-watch #2 (the CC Target adapter becoming de-facto spec because no
second Target ships) is also implicated: aboot's vendor binding is currently the only
concrete hook-binding in the catalog. Until a second runtime binds the universal
core, the universal/vendor split is unproven under load. The existence of the split is
not proof it works.

## Open questions

None beyond the namespace-discipline watch. The universal/vendor cut itself is the
load-bearing claim to pressure.

Specific open questions:

1. **The universal provides vocabulary.** What tags belong in the universal core's
   `provides`? The split is only enforceable if the tag vocabulary is defined. This is
   the first concrete act of namespace governance.

2. **One component or two?** Is aboot one Capability component with vendor-specific
   relations, or two registered components (universal core + CC binding)? The ground
   truth does not specify. The two-component model is cleaner structurally but requires
   the catalog to handle the dependency. [open]

3. **Componentization path.** `write-resume.sh` is a bash script. The CC projection
   calls for `bin/aboot` (a proper binary / entry point). What is the implementation
   language for aboot's executable? Python matches the CLI tier (§7); bash stays
   simple but is not agent-operable in the `--skill` pattern. [open]

4. **Second runtime as proof.** The universal/vendor split is architecturally
   defensible but empirically unproven until a second runtime (geist.sh, a CI hook,
   anything not CC) binds the universal core. Is there a planned forcing function, or
   does this wait for organic demand?
