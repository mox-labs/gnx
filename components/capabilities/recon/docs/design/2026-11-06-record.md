# recon 0.18.0 and 0.19.0: the design record of steps M3 to M6

The decisions taken while building steps M3 to M6 of `REVIEW-recon-2026-11-06.md` §5, where
the spec was silent or left a choice to the builder; the M5 contract v2 entries (0.19.0) are
the last section. Each names the decision, why, the canon it
rests on, and what would make it wrong. The spec's own rulings (`DECISIONS-components-
2026-11-06.md`, G1 to G7 and the recon rows) are not repeated here.

## M3: two layers

### M3-1. The mission's config schema and the published documents stay in the core

**Decision.** `recon.core.domain.models` (the config: `ReconConfig`, its entries, and the section
models `ScheduleSpec`, `SubscriptionSpec`, `ChangesSpec`, `RangeSpec`, `RetainSpec`) and
`recon.core.domain.documents` (every `recon.v1.*` document) are the core's. The observe layer owns
the behaviour over them: the span planner (`observe/domain/spans.py`), a schedule's projection and
its ports (`observe/domain/scheduling.py`), a subscription's matching, cleaning and stores
(`observe/domain/delivery.py`), the change join (`observe/domain/joins.py`), and every service.

**Why.** A plan reports every problem at once (the standing rule), so the planner that checks a
mission sees the whole document; it is the core's ("the plan of one act", review §5 M3). A config
schema split into a core part and an observe part that extends it would let the observe layer
add keys the core then has to be told to ignore, for no consumer that needs the split now. The
documents are the package's published face: shapes both layers speak, behaviour in neither.

**Canon.** Interfaces may carry what is unlikely to change [parnas-process:c20]; "a mission is a
typed config" is one (review §1.2). Grow from the minimal useful subset [parnas-modules:c34].

**Wrong if.** A change to observe behaviour forces a change to a core module beyond its config
model, or a split of the layers into two packages needs the observe sections out of the core:
then the schema splits, the observe package extending the core's models.

### M3-2. Changes are derived through a new `Hold.derive`, after the seal

**Decision.** The `Hold` port gains one member, `derive(ref) -> Landed`: a sealed archive of what
is held, opened again under its own writer lock, so it reads `writing` while what is derived from
it (a change table, a told index, the meta recorded again with the change summary) is written. The
core's act seals and lets go; the observe layer derives under the same mission or stream hold.

**The decision it hides.** How a table derived from a sealed archive's own tables is kept with
it: the storage secret (S3) the other members hide, not a new one. The review names it
(`Landing.derive`, C6). It returns `Landed`, the write handle `begin` gives, rather than a new
protocol: the members derivation uses (`write`, `keep`, `record`) are `Landed`'s.

**Why not a hook in the seal.** The review rejects that (C4 (c)): the seal would use the hook,
and the observe layer's correctness would gate the core's. Deriving after the act returns keeps the
act's commit independent of it.

**Wrong if.** A second landing cannot reopen a sealed archive for writing; then derived tables
go to a store of their own, and the change cursor's shape changes with them.

### M3-3. A table sealed under the mission's config with no change summary is pending

**Decision.** `recon.observe.application.changes.pending`: a table is pending when its archive is
sealed (a survey's `finished`; a window's, however it was sealed), it was sealed `ok` (a window's,
as sealed), its meta's `config_sha256` is the config now running, and it has no change summary. A
change reader does not pass a pending table; the next survey or stream run of that config derives
every pending archive, oldest first, into itself, before anything newer (`Derivation.catch_up`).
A table sealed under another config is never pending: it reads as one sealed before `changes:` was
set (rebaselined, as before).

**Why.** Deriving after the seal opens a window that compare-inside-the-seal did not have: a
writer killed between the seal and its deriving, and the instant between the act's release and
the deriving's lock. A reader that passed such an archive would never read the rows written into
it later. The config's digest is what tells "derivation never ran" from "this config had no
`changes:`" without the core recording anything of the observe layer's.

**Canon.** At-least-once at the end that knows [neighbours-systems-evolution:c11]; level-based,
from what was committed [api-design-systems:c35].

**Wrong if.** A config edit between a crash and the next run is common; the pending table then
reads as rebaselined, which loses no row but tells it as a rebaseline.

### M3-4. A failed derivation fails the table's changes, never the archive

**Decision.** A told index or change table that cannot be written (an `OSError` included) is the
table's `changes.error` (kind `store`) and a `changes_failed` warning. It no longer makes the
archive `incomplete` with `archive_unfinished`: the archive was sealed whole before.

**Why.** Ruling R9: the act's commit does not wait on its changes. The table tells nothing and is
no told index, so the next table of its output tells its changes too (Vector F6, unchanged).

### M3-5. The stream's writer tells each sealed window to its caller, with its hold

**Decision.** `Stream.run(..., sealed=)`: after each window is sealed and let go, the writer calls
`sealed(hold, window)` under the stream's hold. The observe layer derives the window's changes and
applies `retain:` there; the writer keeps neither. `StreamPlan` loses `retain` and `held`.

**Why.** A window's changes and its retention are acts over other windows (the chain, the rules),
so the observe layer's. The writer owns the hold for as long as the stream runs, so it hands the
hold to what runs between windows, as `on_window` handed the window before.

### M3-6. The session: `recon.open()` gives `Recon(collection, observation)`

**Decision.** The two layers' driving ports are the attributes of one session, `recon.Recon`; the
module functions are its operations, each the layer's that owns it. `recon.open(root)` is added in
M3, its values and extensions in M4. The command line drives one session.

**Why.** Review C10: "`recon.open(...) -> Recon`, whose attributes are the two layers' driving
ports". A flat method surface on the session as well would be a third copy of the operations.

### M3-7. Retention is the observe layer's policy over the core's `Hold.retire`

**Decision.** Which archives and windows go (each entry's rules, the newest, the last told in, a
subscription's unacked rows) is `recon.observe.application.retention`; retiring one, and the
tombstone's committed ranges (R-TOMB), stay the core's.

**Why.** Review C4: "retention as an operation" in the core, its triggers in observe.

## M4: values in, discovery out

### M4-1. A config value is planned as a file's data, and its archive keeps what it was

**Decision.** `recon.open(...).observation.survey("m", config={...})` (or a `ReconConfig`) plans
the value as a file's data; its bytes, the ones hashed into `config_sha256`, are its canonical
JSON (keys sorted, no spaces, dates in ISO 8601), so one value is one config however it was
built. A value is never written as the mission's `config.yaml`, and no conflict with the
mission's own is checked. Each archive (and window) a value config lands keeps it, under
`config` in its meta, as data, with every URL in it reported as recon reports one elsewhere
(`reported_url`: user information and signature parameters redacted). A config file's archives
keep only its digest, as before.

**Why.** A value has no file to read again, so the archive is the one place what it ran is
kept. The first build kept every config's raw text, and `test_telemetry`'s guarantee caught it: a
source's URL may carry a password, and no archive's meta may hold one. So what is kept is what
recon reports of a config, not its bytes, and only where there is no file. The digest still
names the bytes that ran.

**Wrong if.** A program needs to re-run an archive's value config exactly, credentials and all:
then the credentials belong in declared variables, which is what the security boundary asks.

### M4-2. A landing given to `recon.open` must be one recon's query engine reads

**Decision.** `landing` is a `Store` (`Landing` and `Archives`, the two sides of the one storage
decision, declared in `recon.core.domain.archives` with no member of their own). The composition
root builds DuckDB over it only when it gives its tables' files (`TableFiles`, now a declared
runtime-checkable protocol, checked with `isinstance`: ruling G3); any other store is refused
`usage` when the session opens.

**Why.** No second landing exists (review C6 adds a by-value one only when a flow needs it), so
the seam is the archive directory at another place, or wrapped (a test's faults). Refusing at
open is a plan-time refusal, not a query that fails later.

**Wrong if.** A by-value landing arrives: it brings its own `ArchiveQuery`, and `landing` takes
the three ports together.

### M4-3. `extensions` takes in-process collector types and transforms as a `Plugins` value

**Decision (interim, within this series).** In M4, `recon.open(extensions=Plugins(...))` adds
collector types and transforms in-process beside the installed ones; a name an installed one
has is refused `usage`. M5 replaces it with registrations on matrix's registry, at every point.

### M4-4. One default session per project; `RECON_ROOT` is the command line's

**Decision.** The module functions run over `recon.composition.default(root)`: one session per
resolved project, opened on first use and kept for the process, so a call no longer rebuilds
the root. The process environment is read as it is at each call (a live mapping). `--root` and
`RECON_ROOT` are the command line's; the library takes its project as an argument, or finds it
around the working directory, and reads no variable of its own for it.

**Why.** Review M4: "Delete `api._root`'s per-call rebuild". A library that read `RECON_ROOT` too
would make one value come from two places.

**Wrong if.** A long-running program installs a plugin and expects the module functions to see
it: then it opens a session again with `recon.open`.

### M4-5. Provenance: every leaf of the config's own models, given or filled in

**Decision.** `recon.core.application.plan.effective` walks the config's own models (the top
level, each source, each entry, each subscription) and reports each leaf the plan's other
reports do not: `mission` when written, `recon` when filled in, a note when unset means
something (`deadline: null`, an empty `auth.token`). A section with its own report (a stream's
window, a crawl, a range, change detection, a schedule) is that report's to say; a section left
out that turns a feature on (`window:`, `paginate:`, `changes:`, `range:`) is off and no default.
A type's own settings are the mission's and show in each run.

**Canon.** A default is never hidden (ruling G2); explicit defaults [api-design-systems:c38].
matrix 0.9's plan does the same walk (`matrix/composition/effective.py`).

## M5: the matrix seam and the registry (contract v2 not reached)

### M5-1. What M5 delivers, and what it does not

**Delivered.** `matrix>=0.9,<0.10`; `recon/_matrix.py`, the one module that names matrix (a
`single_importer` rule and a test); recon's points `recon.collector` and `recon.transform` on
matrix's registry, owned by `recon`; the built-ins registered from recon's own
`matrix.extensions` entry point; short names for built-ins, type URLs for everyone else (R3);
in-process extensions at every point (`recon.open(extensions=[register])`, U3); the
`recon.collectors` and `recon.transforms` groups deleted; every optional member of a recon
contract declared as a protocol and read with `isinstance` (G3); `_`-prefixed normalize columns
refused (R18).

**Not delivered: contract v2.** `Body` and `Record` items, `Paged`, the core doing raw capture,
conversion, extraction and normalization for every type (R-NS), converters and source kinds as
points, `web` folded into `api` plus the HTML converter (R10), the conformance kit and a client
type passing it, and the deletion of `CollectorType` v1. What an entry at `recon.collector` builds
is still the v1 descriptor.

**Why not.** R-NS cannot be done type by type: the `api` type normalizes before it gives a
record its `_position`, and a resumed crawl finds where it left off by comparing normalized
records, so moving normalization into the core moves crawl resumption with it. That is C7's
`Paged`, and with `Body` items it is a rewrite of every built-in and of their tests, which could
not be done to the standard in this series. A partial v2 would have shipped a contract that
breaks again when the rest lands.

**What it costs.** One more break of the provider contract when v2 lands (review §5: doing the
registry first breaks providers twice). No provider outside recon exists (review §3, Q7), so the
second break reaches recon's own built-ins alone. (Contract v2 landed in 0.19.0, with `Paged`
carrying crawl resumption into the core: M5-7 to M5-18.)

### M5-2. An entry at a recon point builds its descriptor with no config and no need

**Decision.** `registry.register("recon.collector", url, build)` where `build()` gives the
collector type (a transform's callable at `recon.transform`). recon reads each entry back
(`_matrix.plugins`) and builds it itself, rather than through `Registry.create`, since a type's
per-entry settings are validated by the plan from the entry's settings, not from one config the
registry holds. Contract v2 moves the type's needs (requester, shell, clock) onto the entry.

### M5-3. A type URL's segments are kebab-case; a config's short names keep their spelling

**Decision.** matrix refuses `recon.v1.transform.inverted_index`, so the built-in is
`recon.v1.transform.inverted-index` and the config keeps `$inverted_index`; the seam converts
between them for built-ins alone (`type_url`, `short`). A third party's name is its type URL as
written.

### M5-4. Matrix's refusals are recon's at the seam

**Decision.** An in-process extension that matrix refuses (a type URL with no version, one
registered already, a point recon does not declare) is a recon `UsageError` saying why: no matrix
error escapes `recon.open`. An installed extension that fails is quarantined whole by matrix, and
recon reports it under `matrix.extensions`, as `recon types --json` and `recon status` show.

### M5-5. Discovery loads every installed extension; recon's own guarantee is narrowed to its own

**Decision.** matrix loads every `matrix.extensions` entry point, so a session imports each
installed package's registration; in this workspace ix's imports `httpx2` at module level. The
guarantee that planning and status load no heavy library is now held of recon's and matrix's
own registrations (`test_layering`), and the cost is said here: about 0.3 s and ix's imports on
each session's first use (review C3, consequence 3: reported, not worked around).

### M5-6. Underscore columns are refused everywhere; a replay keeps `_position` from its capture

**Decision.** R18 refuses a normalize column that starts with `_`, on any entry. The replay
test that wrote `_position` through a capture entry's spec now checks the replayed records'
content and, apart, each position against its capture frame.

## M6: the component face

### M6-1. Three members over application functions, by reference, in the seam

**Decision.** `recon.v1.component.plan`, `.collect` and `.changes` are thin adapters in
`recon/_matrix.py` over matrix-free application functions: `Observation.spans`,
`Collection.collect(spans, sink=)` and `Observation.changes_of(act)`. `collect` hands each act's
row over as its archive seals, through the sink; `records: true` hands each sealed table's
records over too, as rows of its entry's `type_url`. The core runs on a worker thread
(`asyncio.to_thread`), each row handed over on the run's loop and waited for, so it is durable
when the worker goes on; the run's stop asks the stream's `StreamStop`.

**Why.** Review C1 and ix's pattern. A row per act as it seals is what keeps a killed run's
sealed acts.

### M6-2. `collect` computes no span; a ranged table must be given one

**Decision.** `Collection.collect` runs the mission's snapshot tables in one act, each ranged
one asking for its span's source time, and one window of each stream a `window` span names. A
ranged table with no span, a span of another mission, or of an output the mission does not make
is refused (`usage`). Since-last is the observe layer's (`recon.v1.component.plan`).

### M6-3. A member's project is its config's `root`, else matrix's `cwd`

**Decision.** A member is built from `{mission, root, kinds}` with matrix's `cwd` need: it opens
a session over `root`, or over the directory the host composed for, and refuses at build time
(matrix's `ConfigError`) a mission its config cannot plan. No host need of recon's own.

### M6-4. `changes` derives under the hold, after catching up

**Decision.** `changes_of(act)` takes the hold of the act's mission (or its stream), derives
every pending archive oldest first (the act's own is pending until then), and hands over each
change row of the act's change tables with the `id` a reader gives it, so a flow's change rows and
a subscriber's are the same rows.

## M5, completed: collector contract v2 (0.19.0)

Contract v2 lands whole: the `Collector` Protocol of review C7, its items, `Paged`, `Preflight`,
the `recon.source` and `recon.converter` points, the core doing raw capture, conversion,
extraction and normalization for every type (R-NS), `web` folded into `api` (R10), the
conformance kit, and the deletion of `CollectorType` v1. What follows is where the spec's sketch
was silent or did not fit, and what was chosen.

### M5-7. A collector is built once per act from its needs; its settings arrive in each run

**Decision.** An entry at `recon.collector` is `build(**needs)` with the needs it names
(`NEEDS`: `requester`, `shell`, `clock`, `telemetry`, `deadline`, `rate_limiter`,
`credentials`, `env`, `user_agent`, `project`, `capture_logs`), built once for each act (a
survey, a stream's run, a checked dry run). The entry's `config` is the schema of the type's own
keys in a collector entry; recon validates each entry's keys against it and hands the value to
every member as `Run.settings`, filled for the run.

**Why not `build(config, **needs)` as C7 sketched it.** One collector serves every table of its
type in an act, so it may hold a session across them (a tested contract:
`test_a_collector_keeps_a_stdio_server_across_its_tables_and_recon_ends_it`, the mcp type's one
server per source). A build per entry's config would start a server per entry; and a ranged
table's settings change at every step (`{range.start}` filled), so the value a member needs is
the run's, not the build's. ix's adapters are built the same way (`ix.extension`: built with
needs, options per call). The cost: at recon's points `config` is a schema recon reads and does
not pass to `build`, unlike matrix's own points; the kit fails a build that wants it.

**Wrong if.** A type needs per-entry construction (a client per endpoint): it keeps one per
entry itself, keyed by the run.

### M5-8. recon builds every type once per session with stand-in needs, to read what it declares

**Decision.** `effects`, `records`, `accepts`, `describe` and `check` are members of the
collector (C7), and a plan is pure (R11), so recon builds each installed type when it reads the
registry, with stand-ins for the needs that would reach anything (`requester`, `shell`,
`credentials`, `env`, `project`, `capture_logs`), which fail if used. A build that uses one, or
gives no `Collector`, is a broken plugin. `Paged` and `Preflight` are found with `isinstance` on
that instance. A build must therefore be pure; the docs say so.

### M5-9. `Position`, not `Checkpoint`; `accepts` is a member

**Decision.** A stream resumes a run with `collect(run, Position(value))`. "Checkpoint" already
names the range progress committed at a table's seal (M2), and one word for two things would be
read as one. A collector names the source kinds it runs against as `accepts` (C7: "a collector
names the kinds it accepts", left to the builder): a data member beside `effects` and `records`,
since fan-out needs it statically, before any run. A type whose runs need a source says so in
`check(run)` (`source_needed`), which replaces v1's `requires_source`; an entry that makes no run
(no source in the catalog of a kind it takes) is still checked, as a run with no source, its
source's problem left to the plan's own.

### M5-10. A body carries what its capture records; a body may arrive in chunks

**Decision.** `Body(media_type, data, request)` as sketched, and keyword fields each built-in
needed: `converter` (a converter by name: `api`'s `response_format`, `mcp`'s result reading,
the `capture` type's formats), `kind`, `status`, `headers` (what the capture line records: `api`'s
`http`, `cli`'s exit code), `secrets` (credential values recon keeps out of the capture and out
of nothing else: `api`, `mcp`; the archive tests require records to keep what a server echoed
while captures do not), `origin` (named in a conversion's error), `page` (a capture of a page
replays to the same `{page, i}`), `fields` (`cli`'s `_pattern`, written with each record), `scope`
(`capture`'s `_capture`, read by normalize and never written), and `unfit` (M5-12). `data` may be
an iterator of chunks (a command's stdout), converted and captured as it flows; its generator may
return a `BodyEnd(status, request)` (the exit code is known only at the end).

**The falsifier, read.** C7's falsifier is a type-specific branch in the core, or a client type
needing a member the contract lacks. Neither happened: the core dispatches on item kinds alone,
and the client types (`tests/client_type.py`) use none of these fields. The sketch was thinner
than the built-ins, which is what the fields record.

### M5-11. Converters are picked by name or by media type; mcp's result reading is one

**Decision.** `recon.converter` entries claim media types (`type/subtype`, `+suffix`,
`type/*`); a body that names a converter gets it, else its media type's most specific claim.
Built-ins: `json`, `xml`, `lines` (streaming), `document` (markitdown), and `mcp_result`, which
reads an MCP tool's result as its structured content or the JSON of its text, as the mcp type
did. A body names its converter so that a capture keeps the server's real content type, and
`response_format: document` always means the document converter whatever the content type.
`$markitdown` reads its file in the markitdown adapter and converts the bytes through the same
`MarkitdownConverter.document` the converter uses (C9's unification). The `DocumentConverter`
port is gone; `recon.open` takes no converter.

### M5-12. `extract:` is every type's; a body says whether a misfit fails or skips

**Decision.** recon finds the records in every converted value and every record's data, so every
type takes `extract:` (a relaxation: v1 refused it on `cli`, `tail`, `sse`, `mcp`'s siblings). A
value it does not fit raises `NoRecordsError` as v1's `to_records` did (empty table and a warning
before the first record, a failed table after), unless its body says `unfit="skip"`: the capture
type's bodies, one of many tools' results in a log. A first build skipped every misfit, which a
test caught (`test_a_later_page_that_holds_no_records_where_extract_says_fails_the_table`: an
error page mid-crawl must fail the table); the field is that test's lesson.

### M5-13. The core captures for every type: one rule of redaction, one capture per body

**Decision.** A whole body is captured as given, each of its `secrets` redacted: a JSON body value
by value (a short credential only where it is a whole value), written again only when something
changed; any other as text. A streamed body's chunks are redacted as text. `cli` gives one body a
command, so a mission with `patterns:` keeps one capture a command (v1 kept one per entry, its
commands concatenated). A replaying `capture` table is captured too, with the original's `kind`
and request, so a replay archive kept with `preserve_raw` replays itself.

### M5-14. `web` and its source kind go; the replacement's record

**Decision.** Ruling R10 removes `type: web`, the collector's and the catalog source's (a web
source was an HTTP endpoint by another name); each is a plan problem whose fix says what to write
(`REMOVED_TYPES`, `REMOVED_KINDS`: data, not a branch). The replacement is `api` with
`response_format: document`, one record `{url, title, content, content_type}`: `status_code` is
dropped, since a body that reaches conversion was a success. `api`'s `response_format` takes
`json`, `xml`, `text` (lines) and `document`; `html`, which v1 refused at plan time, is no value.

### M5-15. No path in a need but the person's own

**Decision.** `mission_dir` leaves what a type is handed (G5): the `capture` type reads logs
through `capture_logs` (`MissionCaptureLogs`, the file store's), and a `file:` credential is
resolved by the `credentials` need over the mission's directory. `project` stays a need: it is the
person's directory (as `MissionStore.project` is), where an mcp stdio server runs. A transform's
`base` is bound by recon for the runs of a `local` source, the core's rule for the kind it already
confines transforms to.

### M5-16. What `recon.v1.types` says of kinds and converters

**Decision.** `sources[].added_by` (the collector type that added a kind) is replaced by
`origin` (whose the kind is) and `summary`, as kinds are entries of their own; `converters` is
added; `capabilities` names `paginate` and `preflight` only, as every type takes `extract`. A
beta document changed in a minor release, said in the CHANGELOG.

### M5-17. The conformance kit is recon's own module, and checks behaviour

**Decision.** `recon.testing.CollectorConformance` (modelled on `matrix.testing`) registers a type
in-process, reads it as recon does, plans its entry through a session, runs its items through
recon's pipeline (`recon.testing.records`), closes a run early and from another thread, resumes a
stream's run after a position, and exercises `Paged` and `Preflight`. Every built-in passes it
(`tests/test_builtin_conformance.py`), and so do two client types written as an outside package
writes them (`tests/client_type.py`, which imports only `recon.extension`). The kit itself fails
a type that breaks the contract (`tests/test_conformance.py`). Its clock reads no time: it moves
by the waits asked of it, so the clock-port rule holds of the kit too.

**Wrong if.** Two of the first three outside types fail the kit for a reason the contract does
not need (review §6.2): then the kit demands too much.

### M5-18. A trap the contract keeps: `records` is a member

The contract's `records` (`finite`, `unbounded_*`) is a natural attribute name. A test fake that
kept its data as `self.records` made recon read a list as the type's records kind; mypy caught it
(`tests/test_changes.py::_Feed`, renamed). The name is C7's and stays; the guide says what it is.
