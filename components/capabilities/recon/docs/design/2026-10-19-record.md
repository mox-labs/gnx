# recon 0.11.0 and 0.12.0: design record, 2026-10-19 to 2026-10-22

The judgments made bringing recon to the shared exit-code and error contracts, the CLI and
API audit's findings (S12, S13, S14, S15, N1, N2, N8) and telemetry on OpenTelemetry. The
form is `crafting-aces`' record: one row per judgment, the test it answers to with its
mark, a verdict, the named weakness or measure, and tagged evidence. Paths are relative to
`components/capabilities/recon/`; "audit" is the CLI and API audit of matrix, ix and recon
of 2026-10-19 (reported), whose findings are named by their ids.

## Claims (draft for the owner)

A draft of recon's claims as of 0.12.0, written by the builder from the code and the tests at
this release, for the owner to confirm or rewrite: the owner's words decide. The measures and
the parties are as the gate review of 2026-10-22 tightened them, each to what its cited tests
hold. Each is R(X, Y, W, M): X the system, Y the property kept and for whom, W the class of
change it is kept through, M the measure and its value now. Test ids are relative to
`components/capabilities/`. 0.11.0's public-surface claim (next section) still holds as
written; its two contract tests pass unchanged.

(`api`, `cli`, `web`, `capture`, `mcp`) and `recon.transforms` five, all written by recon's

## The claim

R(recon's public surface: the CLI, `import recon`, the `recon.v1.*` documents, the archive
layout; Y: an agent or program driving recon acts on one error shape, one exit table and
one problem vocabulary shared with matrix and ix, and can see what a survey did without
reading code; W: a sibling tool's agent reading recon's output, a program calling the
library from another directory, an operator pointing telemetry at a collector of their
choosing; M: the contract tests in `tests/test_cli.py` (`test_the_agreed_kinds_keep_their_
agreed_codes`, `test_the_shared_problem_kinds_are_the_agreed_ones`) pass, and every audit
finding listed has a regression test that failed before its fix). aces-claims T1, T2
(attested): the four parts are present. The procedure ran on an existing component, so
steps 2 and 3 were asked as questions of the layout already there; step 9 (slick manifest)
is pending: `slick` was not run, and no manifest was written from memory.

**The 2026-07-28 revision is what this SDK speaks, by default.** `mcp_types/version.py` lists
2026-07-28 as the one `MODERN_PROTOCOL_VERSIONS` entry ("the stateless per-request
envelope") beside the four handshake versions; FastMCP's `Client` defaults to `mode="auto"`
(`fastmcp/client/client.py:128-134`), which probes `server/discover` at 2026-07-28 and falls
back to the `initialize` handshake for any server that is not positively modern
(`mcp/client/_probe.py`). Observed: the SDK's own server (the test fixture) and
`@modelcontextprotocol/server-filesystem` 2026.8.31 both negotiated 2026-07-28 over stdio. What
it means for a stdio server: at 2026-07-28 there is no handshake and no session state, every
request carrying its own envelope (`mcp/server/runner.py`, "Serve a 2026-07-28 connection"), so
the process holds no protocol session to preserve, and keeping it alive across tables saves
only its start (an interpreter, or `npx -y` downloading a package); a handshake-era server
does keep a session on its connection. One process per source for the survey serves both.

**OAuth gateways stay on the hook route.** FastMCP's `OAuth` (`fastmcp/client/auth/oauth.py`)
stores tokens in any `AsyncKeyValue` (memory by default, with a warning; the client extra
brings `py-key-value-aio`'s keyring and file-tree stores), and the SDK's provider refreshes an
expired token with its refresh token without a browser (`mcp/client/auth/oauth2.py`,
`_auth_flow`). But the first authorization, a refused refresh, or any 401 runs the full
authorization-code flow: `redirect_handler` calls `webbrowser.open` and `callback_handler`
serves a local callback for up to 300 s. Headless, it works only after an interactive login
left a refreshable token, and when the refresh is refused it opens a browser and waits five
minutes. A deterministic collector never prompts, so it would need a recon login command and a
persistent token store (no keyring backend on a headless Linux host): not built, as ruled. The
client also ships `ClientCredentialsOAuthProvider` (`fastmcp/client/auth/client_credentials.py`,
the `client_credentials` grant, no browser): a gateway that offers it could be a deterministic
source. That is an owner's decision, not taken here.

## Not done, and why

- The lock-free append to a table's waiting lines (`archive_files._Lines`) relies on a list's
  `append` and its slice deletion each being atomic: under the GIL they are; on a
  free-threaded build PEP 703 gives lists per-object locks, which should keep them so, but
  that is not verified here (no free-threaded build was run).
- Half-made archives a dead survey left (`.<archive id>.<pid>.making`) are reported by
  `recon status` (`archive_abandoned`), never removed by recon: removing is the owner's
  call, and a pid reused since reads alive, so such a leftover goes unreported.
- Streams, later (B9): websockets, webhooks, MCP notifications, Parquet compaction of sealed
  windows, `align:` for windows on a grid of the clock, and more than one stream per process.
- A third party's collector type with no `close()` that ends a read in progress can hold a
  stream's stop until its next record: past `stop_s` it is a `source_stuck` warning and its
  thread is left. The built-ins all have one (`cli`'s kills its command's process group).
- A window's end marker waits outside the buffer's bound (B5's row): bounding them too needs
  the writer to skip empty windows it is behind on, which would change what a quiet source's
  windows are; left for the owner.
- The slick manifest (step 9): `slick` was not run; the contract is pending, with its fields
  given by the ports listed in the README's Design section.
- Measuring the cost of telemetry on a large survey: needs an experiment (a survey of
  10,000 requests with and without an SDK installed), not run.
