# matrix 0.10.0: design record, 2026-11-06

The judgments made building matrix 0.10.0, step 3 of the component fix-up: the model-runtime
seam, the bridge that carries hardline across it, extension discovery, and where a model
call's session row learns which runtime answered. Rows take the form
of the earlier record (`2026-10-19-record.md`): decision, alternatives weighed, verdict and
why, named weakness, evidence. Evidence tags: *observed* (read or run on this tree today),
*reported* (a dated document), *inferred*. "The decisions" is the fix-up's decision sheet
(`DECISIONS-components-2026-11-06.md`, rulings G1 to G7, M-O1 to M-O8, HO1 to HO9, M-DISC);
"the hardline review" and "the matrix review" are `REVIEW-hardline-2026-11-06.md` and
`REVIEW-matrix-2026-11-06.md`, all kept outside the repository (*reported*).

This record supersedes, in the earlier one: §14's field-by-field map of hardline's record onto
`ModelCall` and the session row; §18's pydantic-ai runtime built on hardline and its
`usage_counted_by`; §19's `pydantic_ai_model` as an optional member of the port.

## 1. The model-runtime seam (rulings HO1, M-O1 to M-O3, M-O5, M-O6, M-DEP)

|---|---|---|---|---|
| **matrix depends on no model runtime.** hardline leaves matrix's dependencies; no module of matrix imports it; the layer map forbids it in every layer. The adapter is a separate distribution, `matrix-hardline`, which depends on matrix and hardline and registers from its own `matrix.extensions` entry point | (c) matrix keeps the dependency and one seam module (the hardline review's recommendation); (b) hardline depends on matrix and holds the adapter; (d) a shared contract package | the owner ruled (c′) on 2026-11-06 ("wack architecture"). Refusing an unregistered one would fail every run wired without the registry's schemas (a test's `wire({...})`), so an unregistered document is kept as it is, as a kind without a schema is | a runtime that registers no schema is unchecked | *observed*: `tests/test_sessions.py::test_a_session_s_provenance_is_held_to_the_schema_registered_for_its_type_url` |

What a failed call carries is the bridge's own document, `matrix-hardline.v1.failed-call` | keep `matrix.v1.model-runtime.hardline` (short name `hardline`), which every config, ix test and stored row named; `hardline.v1.model-runtime`, on hardline's behalf | a type URL in matrix's namespace for a runtime matrix does not ship is the privilege the ruling removes, and the namespace rule (a distribution owns its own root, G7) says whose it is. The failed-call document is the bridge's composition of hardline's error fields, so it is the bridge's. hardline's `CallRecord` is hardline's document, whole | every config moves to the full type URL; the bridge's name is provisional, and a rename moves its type URLs, which are stored in session rows (a one-way door) | *observed*: `matrix-hardline/tests/test_bridge.py::test_it_registers_its_runtime_and_the_schemas_of_what_it_records` |
| **With no model runtime that calls a model installed, a config that names one is refused when it is composed**, and the fix names what to install (`pip install matrix-hardline`, `matrix-hardline.v1.model-runtime`). The pointer is one constant in the composition root, said only when every installed model runtime is a stand-in | a default runtime in matrix; nothing (the generic "install the package providing it") | a refusal at `matrix check`/`plan`, before anything runs, never a late crash. With none composed, or several, the key is a `missing_key` problem listing them. **The falsifiers, checked.** The hardline review's D1 falsifier (2), "the adapter cannot be
written without matrix's domain naming a hardline type", did not fire: matrix's domain names
none, and the adapter reaches matrix and hardline only through their `__all__`
(`matrix-hardline/tests/test_bridge_layering.py`). The matrix review's R3 falsifier (1), "a second
model runtime cannot serve the pydantic-ai runtime through the widened port without a new

## 2. Discovery loads what a session's points need (ruling M-DISC)

0.9 loaded every installed `matrix.extensions` entry point into every registry, so a recon
session imported ix's registration and what it imports (httpx2), and recon's guarantee that
planning loads no heavy library had to be narrowed to its own and matrix's registrations (recon
design record M5-5, *reported*). The owner ruled it wrong ("wack architecture", 2026-11-06).

| decision | alternatives weighed | verdict and why | named weakness | evidence |
|---|---|---|---|---|
| **An entry point declares the points it registers at by its name**: one line per point in the `matrix.extensions` group, each naming the same `register` (`"recon.collector" = "recon._matrix:register"`). Discovery reads the names from the installed metadata, imports nothing to read them, groups the lines of one `register` into one extension, and loads only the extensions that declare a point the session names | (a) one entry-point group per point, `matrix.extensions.<point>` (stevedore's namespace per point); (b) a file shipped in the package listing the points; (c) the entry point's `[extras]` bracket; (d) load every extension and drop what the session does not use (0.9) | the session's points are what the discovering code knows; what an extension registers at is what only the extension knows, so it must say so where it can be read without running it. Entry-point metadata is exactly that: the packaging standard's, read by `importlib.metadata` from `entry_points.txt`, with no import (AP:c35, the least costly mechanism that meets the need). (a) changes the group the stable contract names and scatters one extension over many sections, and a full catalog must scan group names by prefix; (b) cannot be read without importing the package (`importlib.resources` imports it), and a file beside `METADATA` is not portable across build backends; (c) the specification deprecates extras on entry points; (d) is the defect | two `register`s of one distribution cannot both be named at one point (a name is unique in a group): fold them | *observed*: `tests/test_registry.py::test_an_extension_is_loaded_only_for_a_session_that_needs_one_of_its_points` |
| **The declaration is held to the code**: an extension that registers at, or declares, a point its entry points do not name is quarantined whole, with a fix naming the line to add | trust the declaration | a declaration that can drift from what `register` does is a promise kept by reading (MD:c34): an extension that forgot a point would be missing from the sessions that need it, silently. Quarantined, it is a failure `matrix catalog` lists, the same in every session that loads it | code registering directly (`Registry.register`, `recon.open(extensions=)`) declares nothing and is trusted, as for type URLs | *observed*: `tests/test_registry.py::test_an_extension_that_registers_where_it_did_not_declare_is_quarantined` |
| **A registry scoped to a session's points keeps the entries at those points and ignores a registration at any other** (`Registry.scope`), after holding it to the extension's declaration; a point inside the scope that nobody declares is still a failure | ignore only a registration at an unknown point outside the scope (which makes what the registry holds depend on load order, when the point's owner loads later); quarantine it (0.9's rule, which assumed every extension was loaded); load every owner of every point an extension names (a closure) | an extension that serves two owners' points (an ix sensor and a recon collector) would otherwise be quarantined in each owner's session, for the other's point; the closure would load ix into a recon session again. Ignoring every registration outside the scope makes the registry hold exactly the session's points, whatever the order | in a scoped session, `entries(point)` is empty for a point outside the scope, and a registration there is not checked beyond its declaration: a caller that reads a point asks for a registry that names it, and `matrix catalog` checks everything | *observed*: `tests/test_registry.py::test_an_extension_serving_another_owner_s_point_is_not_quarantined_for_it` |
| **Who names a session's points**: `default_registry(points=...)` (and `Registry(scope=...)` with `load_extensions`). `compose` and the documents built on it name matrix's points (`MATRIX_POINTS`); `catalog` and `describe` name none, every extension; recon's `plugins()` names recon's four; ix's root names matrix's and ix's | a scope inferred from the config | the caller knows which points it reads; a config does not list the points its components reach through the registry. A host that reaches another owner's point (ix's sensors) names it | a component that reaches the registry for a point the host did not name finds nothing there; ix, the one that does, names its own | *observed*: `recon/tests/test_layering.py::test_importing_recon_loads_no_adapter_and_wires_nothing`, restored to its 0.17 form and passing with ix installed |
| **matrix's existing rules hold**: a broken extension is quarantined and the rest load; a type URL needs a version; two registrations of one type URL are refused, the namespace's owner keeping it; points have owners; an extension at a point declared later is retried | | each is checked where it was, in `Registry.register` and `Registry.load`; discovery decides only which extensions are loaded | | *observed*: the 0.9 registry tests, on entry points named by point |
| **An extension written for 0.9** (its entry point named after itself, `acme = "acme:register"`) is read as declaring a point named `acme`: no scoped session loads it, and a full discovery (`matrix catalog`) quarantines it at its first registration, with the fix | read an unknown name as "every point" | the owner's G1: the old form is deleted in the same release, with no shim; reading it as "every point" would keep 0.9's defect for every extension not yet moved | until it moves, such an extension is missing from every session but the catalog, which names it with the fix | *observed*: `tests/test_registry.py::test_an_extension_that_registers_where_it_did_not_declare_is_quarantined` |

## 3. A session row's runtime comes with the model runtimes (the matrix review, D-7, R2.2)

The review's table of needs dropped `models` and `model_runtime_entries` in R3; 0.10.0 dropped
`models` and missed the other. It was a beta need for one component: the model step read its
own runtime's registry entry there to put the entry's `type_url` and `drives` on every session
row it records. The requirement it served stays: a model step's row names the type URL its
runtime was built from and the distributions that entry drives, as reliably as before.

| decision | alternatives weighed | verdict and why | named weakness | evidence |
|---|---|---|---|---|
| **The `model_runtime_entries` need is gone; the `model_runtimes` need is a `ModelRuntimes`**: the read-only mapping of each model runtime by name, as before, which also says what each was built as, `type_url(name)` and `drives(name)`. `compose` builds one, from the config's `type` and the registry's `drives`, and hands the same one to agent runtimes and to components; the model step's builder reads its own runtime's two facts there and gives them to `ModelStep`, which records them on every row, completed, failed or cancelled, as before | (a) the executor stamps the row when it records it, beside the `provenance` check in `record_session`; (b) a bound model runtime, a wrapper carrying its identity as `BoundAgent` carries an agent's; (c) the runtime says its own type URL (a port member, or a `ModelCall` field); (d) a per-component need holding the step's own runtime's identity, as `name` is per component; (e) keep `model_runtime_entries`, made stable; (f) the identity as an optional capability of the mapping, a runtime-checkable Protocol the builder checks with `isinstance` | The identity is the composition root's knowledge (the config names the type, the registry says what it drives) about the runtimes it hands over, so it travels with them; a caller that records a call on one needs both, and `model_runtime_entries` made it declare two needs and join them by name, handed whole `Entry`s (a builder, a config schema, a stability) to read two fields. (a) the executor knows which component recorded a row, not which runtime answered: a component may call several, the knowledge would move from the root into the domain, and it would hold only under an executor the container made, where today it holds under any. (b) a wrapper must forward the optional members (`SupportsAclose`, `SupportsResolved`, `SupportsWarnings`) of a runtime that may lack them, so `isinstance` would lie: a shim (G1, G3). (c) a runtime does not know the type URL it was registered under, and a port does not grow by a feature. (d) and (e) are a need for one component, the defect itself (D-7). (f) fails the matrix review's R4.1 rule, that an optional member's absence changes nothing another part computes: here it would change the row, so the identity is part of the need's declared type | The stable need's type grows, and on the provider side: a host that hands `model_runtimes` itself hands a `ModelRuntimes` (ix's on-demand mapping now subclasses it; nothing in ix reads the two methods). This departs from the review's target table, which kept `model_runtimes: Mapping[str, ModelRuntime]`; every reader of the need still reads it as that. `ModelRuntimes` is an abstract base class, not a Protocol, because `Mapping` is nominal in Python and a Protocol spelling out the mapping would be wider than what it saves; the domain layer admits `abc` for it | *observed*: `tests/test_sessions.py::test_a_model_step_s_row_names_the_type_and_the_distributions_of_its_runtime` (fails when the builder drops `drives`, checked), `matrix-hardline/tests/test_bridge.py::test_the_provider_is_the_row_s_or_else_its_backend_s_on_the_call_and_its_row`, `ix/tests/test_agent_runs.py::test_a_runtime_that_needs_the_model_runtimes_is_handed_them_as_the_need_declares`, `tests/test_contract.py::test_the_stable_needs_are_as_promised` |
